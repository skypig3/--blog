### 1.3 唯一的真实分歧：Spring Boot 3.5 还是 4.1

这是本次选型**唯一需要查证才能定**的问题，因为 MyBatis-Plus 的 starter 是按 Spring Boot 大版本分开发的。

Maven Central 实测数据（2026-10-09 拉取）：

| Spring Boot 版本线 | 最新 GA | 开源支持截止 | MyBatis-Plus 对应 starter | starter 编译时依赖 |
|---|---|---|---|---|
| 3.5 | 3.5.16（2026-06-25） | **2026-06-30 已过期** | `mybatis-plus-spring-boot3-starter` 3.5.17 | Boot BOM 3.5.9 + mybatis-spring 3.0.5 |
| 4.0 | 4.0.8（2026-08-20） | 2026-12-31 | `mybatis-plus-spring-boot4-starter` 3.5.17 | Boot BOM 4.0.1 + mybatis-spring 4.0.0 |
| 4.1 | 4.1.1（2026-08-20） | **2027-07-31** | 同上（4.x 共用 boot4 starter） | 同上 |

淘汰链：

1. 作业答辩在 2026 年 10 月之后，**3.5 已经 EOL**，选它等于一开学就欠一次升级 → 不优先。
2. 4.0 在 2026-12-31 到期，正好卡在答辩期附近 → 不如直接 4.1。
3. 4.1 有官方 MP starter，且 **4.1.1 + boot4-starter 3.5.17 我实测跑通了**（§1.4 R4）。
4. 唯一顾虑：boot4 starter 是照着 Boot **4.0.1** 编的，我跑的是 **4.1.1**，跨了一个小版本 → 实测无异常（构建、启动、CRUD、分页、事务全绿）。

**结论：Spring Boot 4.1.1 + `mybatis-plus-spring-boot4-starter:3.5.17`。**
退路：如果实现过程中撞上 Boot 4 特有怪问题，**降到 3.5.16 只需换两处**——parent 版本号 + starter 换成 `spring-boot3-starter`，业务代码不用动。这条退路我在 §10 风险表里记着。

### 1.4 定向 spike：把 5 组"可能翻车"的点真跑一遍

我没有拿教程当证据。下面每条都在你机器上执行过，原始输出在 `docs/spike/`。

**R1｜中文路径会不会让 SQLite 打不开库？**
担心的是：项目放在 `D:\学习项目\`，驱动是 C 层原生代码，中文目录历史上出过问题。
实测：在项目根下的临时目录（跑完已清理）建库、建含中文的文件名 `测试_博客.db`、插入中文标题、查回来逐字符相等 → **通过**。
附带测到：`supportsGetGeneratedKeys=true`、`busy_timeout` 默认 **3000ms**、`journal_mode=WAL` 写进库头、重启后仍是 wal、`integrity_check=ok`。
证据：`docs/spike/A1-sqlite-jdbc-raw.txt`

**R2｜MyBatis-Plus 的分页插件支持不支持 SQLite？**
这是最容易翻车的一条。事实链（读 MP 3.5.17 源码，不是读博客）：

- `DbType` 枚举里**确实有** `SQLITE("sqlite", "SQLite数据库")`；
- 但 `plugins/pagination/dialects/` 包里**没有 SqliteDialect 类**（只有 MySQL/Postgre/Oracle/DB2/…15 个）；
- `DialectFactory.getDialect()` 的兜底顺序是 `mysqlSameType → oracleSameType → postgresqlSameType`，而 `DbType.SQLITE` 落在 `postgresqlSameType()` 的名单里；
- 所以 `DbType.SQLITE` → 走 **PostgreDialect** → 生成 `LIMIT ? OFFSET ?`，SQLite 原生支持这个写法。

实测确认（真实 SQL 日志，`docs/spike/A3-paged-sql.txt`）：

```
Preparing: SELECT COUNT(*) AS total FROM t_article WHERE (title LIKE ?)
Preparing: SELECT id,title,status,view_count,created_at FROM t_article
           WHERE (title LIKE ?) ORDER BY id DESC LIMIT ? OFFSET ?
→ 第 3 页 / 每页 10 条 / 共 25 条：返回 5 条，total=25，pages=3   全对
```

**结论：`new PaginationInnerInterceptor(DbType.SQLITE)` 可用**，不需要手写方言。
不写 `DbType` 让它自动探测也可以（`JdbcUtils` 认得 `:sqlite:`），但**我们显式写**，少一个变量。

**R3｜SQLite 的并发写会不会锁死？**
实测：开两个连接，A 起写事务不提交，B 也写 → B 在等满 busy_timeout 后抛
`[SQLITE_BUSY] The database file is locked`。
结论：SQLite 是**单写者**模型，连接池给多大都不改变"同一时刻只能有一个写事务"这个事实。
设计决定：**HikariCP `maximum-pool-size: 1`**（见 §4.4）。理由不是"省事"，是"在单写者模型下，池子开大只会把必然排队变成必然报错"。规模是课程演示项目，串行完全够用。

**R4｜整套依赖凑在一起能不能真的启动？**
建了个最小可运行工程：Boot 4.1.1 + MP boot4 3.5.17 + jsqlparser 3.5.17 + sqlite-jdbc 3.53.4.0，Java 21。
`mvn package` → `java -jar` 全绿。下表是 48 项实测结果里与设计直接相关的部分
（完整输出：`docs/spike/stacktest/stacktest-spike.txt`）：

| 测项 | 结果 | 用途 |
|---|---|---|
| `IdType.AUTO` 插入后主键回填 | id 1→25 正确回填 | 文章保存后能立刻拿到 id |
| DDL 里的 `DEFAULT (datetime('now','localtime'))` | MP 读回 `2026-10-09 16:17:12` | 时间字段可以交给库默认值 |
| `update ... where status='PENDING'` 连点两次 | 第一次 1 行，第二次 **0 行** | **防重复审核**的机制成立（§6.2） |

**R5｜过程中真撞到的 3 个坑（已写进设计，避免实现时再撞）**

1. **MP 的 `mybatis-plus-jsqlparser` 不会自动带进来。**
   `mybatis-plus:3.5.17` 的 POM 里它是 `<optional>true</optional>`。
   不显式加这个依赖，`PaginationInnerInterceptor` 这个类**根本不存在**（3.5.9 之后被拆出去了）。
   → pom 里必须显式写这条。
2. **Mapper 不会被自动扫描。**
   Boot 4 + boot4-starter 下，只写 `@SpringBootApplication` 时 `ArticleMapper` 注入失败，
   报 `No qualifying bean of type 'demo.ArticleMapper' available`。
   加上 `@MapperScan("...mapper")` 就好了。→ 启动类上固定加这个注解。
3. **SQLite 不会自动创建父目录。**
   指到 `./noexist/blog.db` 直接抛 `[SQLITE_CANTOPEN] Unable to open the database file`，
   而 Spring 那边只显示 "Failed to execute database script"，看不出真因。
   → 启动前必须先建 `data/` 和 `data/uploads/`（§4.4 第 5 条）。

### 1.6 决策记录（ADR 摘要）

**ADR-001｜认证用 Session + 自研拦截器，不用 Spring Security 全家桶，不用 JWT**
背景：作业 1.5 写的是"**可**使用 Spring Security，配合 Session 或 JWT"——是许可不是强制。
决定：`HttpSession` 存 `userId` + 自定义 `HandlerInterceptor` + 两个注解（`@RequireLogin` / `@RequireRole`）；密码哈希借用 `spring-security-crypto` 里的 BCrypt。
理由三条：

- ① Spring Security 6/7 的过滤器链要能讲清楚，代价远大于这次它能带来的收益；
- ② JWT 在这个场景没有好处——单服务端、无第三方调用，还得额外处理"改密码后旧 token 失效"；
- ③ 报告里"登录鉴权、权限判断"这两段，用 150 行自己的代码能讲得明明白白，
  比贴一段 `SecurityFilterChain` 配置更容易答辩。
代价：自己实现的部分要测全（未登录 401、无权限 403、账号被禁用、改密码后失效）。这四条我在 §6.1 逐条给了实现位置和验收方法。
退路：如果老师明确要求 Spring Security，切换点集中在 `AuthInterceptor` 一个类，替换成本约半天。

**ADR-002｜分页用 MP 的 `PaginationInnerInterceptor(DbType.SQLITE)`**
见 R2。备选（手写 LIMIT/OFFSET）已淘汰，因为实测方言能命中。

**ADR-003｜文章内容存 Markdown 原文，渲染放前端**
决定：库里存 `content_md`（Markdown 源码），前端用 markdown-it 渲染 + DOMPurify 消毒。
理由：① 作业 1.5 允许"富文本或 Markdown 二选一"；② Markdown 存的是纯文本，报告里好解释、数据库里好搜索、以后换前端不丢数据；③ 富文本存 HTML 等于把 XSS 风险写进数据库。
代价：要自己处理图片上传（§6.6）。

**ADR-004｜前后端同一个 Git 仓库、两个子目录**
按作业 6.2「前端与后端应分别放在清晰的目录中」组织，见 §3.5。

**ADR-005｜后台和前台做成一个 SPA，用路由前缀 `/admin` 区分**
理由：省一套构建、省一个端口、权限判断集中在路由守卫里。作业 1.5「页面路由：区分公开页面、登录用户页面和后台页面」正好是路由守卫要干的事。

**ADR-006｜文章/评论用逻辑删除，审核日志只追加**
`deleted` 标记 + 物理保留，避免"删了文章评论还在"的外键孤儿；`t_audit_log` 永不修改，满足作业 2.3.3「记录操作者、目标内容、操作结果、说明和时间」。

| 审核文章和评论 | ❌ | ❌ | ✅ | `@RequireRole(ADMIN)` |
| 下架违规文章、处理违规评论 | ❌ | ❌ | ✅ | 同上 |
| 管理用户、分类、标签、系统设置 | ❌ | ❌ | ✅ | 同上 |
| 查看后台统计和审核记录 | ❌ |  | ✅ | 同上 |

两条硬规则（作业 2.3.2）：

- 注册接口**不接受** `role` 字段，角色一律服务端写 `USER`；
- 系统必须**至少保留一个启用状态的管理员**，禁用/降级前做计数校验（§6.7）。

### 2.2 做什么、不做什么

必做（作业 1.4）：用户管理、文章管理、文章审核、评论与回复、评论审核、分类标签、点赞收藏、基础后台管理。

**明确不做**（作业 1.4 排除项，别顺手加）：邮件找回密码、第三方登录、实时聊天、个性化推荐、全文搜索引擎（FTS5）、文章历史版本。

> 这条对进度很重要：上面每一项看起来都"顺手就做了"，但每一项都会吃掉半天以上，而且作业里明写了"扩展功能应在必做功能完成后开发，不能替代基础功能"。

### 2.3 三条主流程

**流程一：投稿到上线**

```
 作者                后端                    管理员              访客
  │  保存草稿          │                        │                 │
  ├───────────────────>│ status=DRAFT           │                 │
  │  提交审核          │                        │                 │
  ├───────────────────>│ DRAFT/REJECTED         │                 │
  │                    │   → PENDING            │                 │
  │                    │  (记录 submitted_at)    │                 │
  │                    │   待审核列表 <──────────┤                 │
  │                    │                        │  通过            │
  │                    │  PENDING → PUBLISHED <─┤                 │
  │                    │  (CAS: where status=    │                 │
  │                    │   'PENDING')            ├────────────────>│ 能看到
  │                    │                        │  驳回(必填原因)   │
  │                    │  PENDING → REJECTED <───┤                 │
  │  看到驳回原因 <─────┤                        │                 │
  │  改了再提交 ───────>│ REJECTED → PENDING     │                 │
```

**流程二：评论与回复（审核要覆盖回复）**

```
 登录用户 ──> 提交评论/回复 ──> t_comment status=PENDING
                                    │
                       管理员审核 ──┴──> PUBLISHED  → 前台可见（挂在对应文章下）
                                    └──> REJECTED  → 仅自己可见 + 驳回原因
 展示条件：文章 status=PUBLISHED  AND  评论 status=PUBLISHED  AND  评论未删除
 回复通过 parent_id 挂在父评论下；父评论被驳回时，回复一并隐藏（见 §6.3）
```

**流程三：账号被禁用 / 改了密码**

```
 每次请求 → AuthInterceptor 用 session 里的 userId 查库
              ├─ 查不到 / deleted        → 401 请重新登录
              ├─ status = DISABLED       → 401 + 提示"账号已被禁用"，并清 session
              ├─ credential_version 变了  → 401 + 提示"密码已修改，请重新登录"
              └─ OK → 把最新 role 放进请求上下文，再交给 @RequireRole 判断
```

这条流程直接对应作业 2.2.1 的两句话："被禁用账号不能登录，**已有登录状态也不能继续访问受保护数据或执行写操作**"，以及"验证原密码后设置新密码，并**明确修改后登录状态的处理规则**"。

### 3.4 认证与权限方案（细节）

| 环节 | 方案 |
|---|---|
| 密码存储 | BCrypt（强度默认 10），字段 `password_hash`，**任何 VO / 日志 / 错误信息里都不出现** |
| 登录凭据 | 用户名**或**邮箱 + 密码（作业 2.2.1 要求两者都行） |
| 会话 | `HttpSession`，只存 `userId`；每次请求回查库拿最新 role / status / credentialVersion |
| 角色 | `USER` / `ADMIN` 两值；游客 = 没有会话，不是数据库角色（作业 2.1 明确说了这点） |
| 退出 | `session.invalidate()` |
| 改密码 | 校验原密码 → 更新 hash → `credential_version + 1` → 当前会话立即失效 |
| 禁用 | `t_user.status = DISABLED`，拦截器每次请求都查，所以"已登录的禁用账号"下一跳就 401 |
| 归属校验 | Service 层统一入口 `assertOwned(article, userId)`，不靠前端传"是不是我的" |
| CSRF | 同源部署 + Cookie `SameSite=Lax` + 只接受 `application/json`（除上传外）；作为"已知限制"写进报告 |
| 会话持久化 | 不做（进程内）。重启服务后需要重新登录——写进 README 的"常见问题"，避免答辩时以为坏了 |

### 4.4 SQLite 适配清单（全部实测过）

1. **外键默认不启用。** 实测 `PRAGMA foreign_keys` 默认 0。做法：JDBC URL 上带 `?foreign_keys=on`，实测连上后为 1。
2. **pragma 统一写在 URL 上，不用 `connection-init-sql`。**
   实测 URL 参数 `?foreign_keys=on&busy_timeout=5000&journal_mode=WAL` 三项全部生效；
   而 `connection-init-sql` 只执行它自己那一条，journal_mode 仍是 `delete`。URL 方式更省心。
3. **连接池 `maximum-pool-size: 1`。** 依据 R3：SQLite 单写者，池子开大只会换来 `SQLITE_BUSY`。`busy_timeout=5000` 作为兜底。
4. **WAL 模式。** 写进 URL；实测库头会记住这个模式，重开还是 wal，不用每次设。
5. **父目录必须提前存在。**
   实测 `./noexist/blog.db` → `[SQLITE_CANTOPEN]`，且 Spring 侧只报
   "Failed to execute database script"，很误导。
   做法：`main()` 里先 `Files.createDirectories()` 建 `data/` 和 `data/uploads/`，再 `SpringApplication.run()`。
6. **时间存字符串。**
   用 `TEXT` + `datetime('now','localtime')` 默认值，Java 侧映射 `String`。
   理由：SQLite 没有真正的日期类型，存 Unix 秒反而不好读、不好排序；前端直接渲染，不用换算。
7. **中文安全，但排序不是拼音序。**
   实测中文写入/读出逐字符一致，`LIKE '%博客%'` 能命中；但 `ORDER BY title` 走的是 UTF-8 字节序。
   → 列表排序一律用 `published_at / id / view_count`，**不要**提供"按标题字母序"。
8. **`length()` 是字符数不是字节数**（实测 9 字符 / 25 字节），正文摘要截取可以放心用 `substr`，和 Java 的字符下标一致。
9. **建表脚本必须幂等。**
   `spring.sql.init.mode=always` 每次启动都会跑一遍，
   所以 `schema.sql` 全用 `CREATE TABLE IF NOT EXISTS`，`seed.sql` 全用 `INSERT OR IGNORE`。
   否则第二次启动就报唯一约束冲突。
10. **删库重建是万能排障手段。** SQLite 就是一个文件，README 的"常见问题"里写明"关掉服务删 `data/blog.db` 再启动即可重置"。
11. **不要用 `LocalDateTime` 映射时间字段**（实现阶段实测）。
    驱动的 `setObject(LocalDateTime)` 会写成 `2026-10-09T12:34:56`（中间是 `T`），
    而 DDL 默认值 `datetime('now','localtime')` 写的是 `2026-10-09 16:54:20`（中间是空格）。
    同一列混进两种格式后，字符串比较和排序就错了（空格 0x20 排在 T 0x54 前面）。
    所以实体里一律用 `String` + `TimeUtil.now()`，格式与库默认值逐字符一致；
    这条约束由 `TimeUtilTest` 守着（它直接查 `datetime('now','localtime')` 比对格式）。
12. **MyBatis-Plus 的逻辑删除不会改写自定义 `@Select`。**
    `deleted = 0` 必须在注解 SQL 里自己写上，否则会把已删除的文章查出来。
    分页插件同理，`selectHot` 里显式带了 `deleted = 0`。

## 5. 接口设计

### 5.1 约定

- 前缀 `/api`，REST 风格，JSON。
- 统一响应体：

```json
{ "code": 0, "message": "ok", "data": { }, "timestamp": 1759999999999 }
```

`code=0` 成功；非 0 用业务码。**HTTP 状态码同时表达语义**，前端的拦截器只看 HTTP 状态就够决定"跳登录"还是"弹提示"。

| HTTP | 业务码 | 含义 | 前端行为 |
|---|---|---|---|
| 200 | 0 | 成功 | — |
| 400 | 40000 | 参数校验失败（含字段信息） | 表单标红 |
| 401 | 40100 | 未登录 / 会话失效 / 账号被禁用 / 密码已改 | 清 Pinia，跳登录 |
| 403 | 40300 | 已登录但没权限（角色不够 / 不是本人） | 提示无权限 |
| 404 | 40400 | 资源不存在或**不应对当前用户可见** | 空态页 |
| 409 | 40900 | 状态冲突（重复审核、重名、已点赞） | 刷新列表 + 提示 |
| 422 | 42200 | 业务规则拒绝（驳回未填原因、最后一个管理员） | 提示 |
| 500 | 50000 | 服务器异常（不回显堆栈） | 通用错误提示 |

- 分页参数统一 `?current=1&size=10`，返回 `{records,total,pages,current,size}`。`size` 上限 50（后台 100），防翻页炸弹。
- 时间格式 `yyyy-MM-dd HH:mm:ss` 字符串。

## 6. 核心实现要点

### 6.1 登录鉴权与权限判断

`AuthInterceptor.preHandle()` 做四件事，顺序不能乱：

1. 命中 `@RequireLogin`/`@RequireRole` 才处理（用 `HandlerMethod` 读注解）；
2. 会话里没有 `userId` → 401；
3. 回查 `t_user`：不存在 / `deleted=1` / `status=DISABLED` / `credential_version` 与会话记录不一致 → 清会话 + 401（每种情况给不同 `message`，方便答辩演示）；
4. 角色不匹配 → 403。

写进报告的一句话：**"权限判断不信前端，不信 Cookie 里的旧快照，每个请求都回库拿最新的 role 和 status。"** SQLite 单次主键查询是微秒级，池子只有 1 个连接，这个代价可以忽略。

### 6.2 文章审核与"防重复点击"

作业原话：*审核只对当前待审核内容生效，不得通过重复点击将已撤回或已删除的文章错误发布。*

做法是**把状态判断放进 UPDATE 的 WHERE 里**（CAS），而不是"先查再改"：

```java
int rows = articleMapper.update(null, new LambdaUpdateWrapper<Article>()
        .eq(Article::getId, id)
        .eq(Article::getStatus, "PENDING")          // ← 关键
        .eq(Article::getDeleted, 0)
        .set(Article::getStatus, "PUBLISHED")
        .set(Article::getPublishedAt, now)
        .set(Article::getAuditUserId, adminId)
        .set(Article::getAuditedAt, now));
if (rows == 0) throw new BizException(CONFLICT, "该文章当前不是待审核状态，请刷新后重试");
```

实测证据（`docs/spike/stacktest/stacktest-spike.txt`）：同一条 PENDING 记录连点两次 → `1` 然后 `0`。
"先查再改"在并发下会双双通过，这种写法只可能有一个成功，且天然覆盖"已被作者撤回（变 DRAFT）""已被删除（deleted=1）"两种情况。
审核成功后，同一个 `@Transactional` 里写一条 `t_audit_log`。

### 6.3 评论审核（要覆盖回复）

- 回复和顶层评论同表，用 `parent_id` 区分，所以"审核覆盖回复"自动成立——列表页把 `parent_id` 一起带出来即可。
- 可审核状态是 `{PENDING, REJECTED}`：被误驳回的评论必须还能重新放行，否则它永远发不出去
  （作业没写这条，是实现时发现的缺口；文章仍严格只允许 `PENDING`，因为作业 2.3.3 明说了）。
- 展示条件：文章 `PUBLISHED` **且** 评论 `PUBLISHED` **且** 未删除。
- 父评论被驳回或删除时，其下回复**一并隐藏**（在查询里按"顶层已发布"过滤），避免出现"悬空回复"。
- `comment_count` 只在"评论从非 PUBLISHED 变成 PUBLISHED"和"删除已 PUBLISHED 评论"时增减，同事务内更新，避免计数漂移。

### 6.4 数据归属校验

统一在 Service 层，不在 Controller：

```java
private Article loadOwned(Long id, long userId, boolean admin) {
    Article a = articleMapper.selectById(id);
    if (a == null) throw new BizException(NOT_FOUND);
    if (!admin && !a.getAuthorId().equals(userId)) throw new BizException(FORBIDDEN);
    return a;
}
```

列表类同理：`/api/my/**` 一律强制 `eq(Article::getAuthorId, currentUserId)`，**用户 id 从会话取，不从请求参数取**。这条是作业"数据归属校验"最容易被扣分的地方，报告里会专门画一张图。

### 6.5 热门文章规则（作业要求在报告里写明）

```
候选：status=PUBLISHED 且 deleted=0 且 published_at 在最近 30 天内
分值：score = view_count + 2 × like_count + 3 × collect_count + 1 × comment_count
排序：score DESC, published_at DESC
数量：取前 10，每次请求实时计算（不缓存），SQL 一条搞定
兜底：30 天内不足 10 篇时，放宽到全量已发布（否则新库演示时热门区是空的）
```

系数是拍的（阅读是弱信号，收藏是强信号），会在报告里明说是设计选择而非算法结论。

### 6.6 上传与 XSS

- 只允许 `jpg/jpeg/png/gif/webp`，单文件 ≤ 2MB，服务端用扩展名 + 大小 + 真实魔数三重校验；
- 文件名一律重新生成 UUID，**不使用客户端给的名字**（防路径穿越）；
- 存 `data/uploads/yyyyMM/`，库里存相对路径 `/uploads/yyyyMM/uuid.png`，通过 `WebMvcConfig` 的 `addResourceHandlers` 暴露；
- Markdown 渲染：`markdown-it` 关掉 `html:true`，再过一遍 `DOMPurify`。**任何用户输入都不以 HTML 形式回显**。

### 6.7 "至少保留一个启用的管理员"

```java
// 禁用 或 降级 之前
if (targetIsLastActiveAdmin(targetId)) throw new BizException(42200, "系统必须保留至少一个启用状态的管理员");
```

实现：`SELECT COUNT(*) FROM t_user WHERE role='ADMIN' AND status='ACTIVE' AND deleted=0 AND id<>#{target}`，为 0 就拒绝。
初始管理员由 `seed.sql` 用 `INSERT OR IGNORE` 建（密码 hash 由一个一次性小工具生成后写死进脚本，README 里注明是演示账号）。

### 与本文原设计不同的三处

1. **Service 不拆 `interface + impl`**。原设计写了要拆，实现时判断：这个项目里每个域只有一个实现，
   拆接口只会让"审核逻辑在哪"这个问题多绕一层。现在是一个域一个 `@Service` 类。
2. **复杂 SQL 用注解（`@Select` / `@Update`）而不是 `mapper/*.xml`**。
   少一处 namespace 对不上的失败面，而且 SQL 就贴在方法上，答辩时好指。
3. **评论的可审核状态扩到 `{PENDING, REJECTED}`**。被误驳回的评论否则永远发不出去，
   这是端到端测试跑到"驳回后再放行"那一步时暴露出来的缺口；文章仍严格只允许 `PENDING`。

### 实现阶段新撞到的三个坑（都已写进代码注释）

1. **`LocalDateTime` 映射会让同一列出现两种时间格式** → 见 §4.4 第 11 条。
   这是最隐蔽的一个：不报错，只是排序悄悄错了。
2. **MyBatis-Plus 的逻辑删除不改写自定义 SQL** → 见 §4.4 第 12 条。
3. **`LambdaUpdateWrapper.set(condition, column, value)` 的 value 是提前求值的**。
   审核通过时 `reason` 是 `null`，写 `dto.reason().trim()` 直接 NPE → 500。
   必须先做空值归一再交给 wrapper。端到端测试第一轮就抓到它。

### 实现阶段新增的两条实测结论（原设计没预料到）

1. **相对路径 `./data/blog.db` 会被启动目录坑**（已修）。
   命令行 `java -jar` 的工作目录是 `backend/`，而 IntelliJ 的运行配置默认是**项目根**，
   两边各自打开了一个 `blog.db`：一份灌了演示数据、一份只有初始账号，
   现象是"页面为什么是空的"，而且两个进程互相看不见对方的写入。
   现在 `BlogApplication.resolveDataDir()` 按"当前目录有没有 pom.xml / 有没有 backend/pom.xml"
   判定仓库位置，把数据目录固定成 `backend/data` 的绝对路径，
   再作为系统属性喂给 `${blog.data-dir}`。启动日志会把真实路径打出来。
2. **路由守卫只在需要登录的路由上查会话，会让刷新后的公开页面把已登录用户当游客**。
   Pinia 在整页加载后是空的，`/articles/110` 这种公开路由不查 `/auth/me`，
   于是顶栏退回"登录/注册"、详情页点点赞被提示先登录（Cookie 其实还在）。
   修法：`store.checked` 为 false 时无条件先查一次，一次页面生命周期只发一发请求。
